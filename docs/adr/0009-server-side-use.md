# ADR-0009. Серверное использование

- Статус: Предложено
- Дата: 2026-11-09

## Контекст

Нужна возможность строить на krtc серверы. Под «сервером» понимаются три разных класса задач:

1. **Серверный участник звонка**: боты, запись, шлюзы (SIP ↔ WebRTC), MCU со сведением, нагрузочное тестирование. Ведёт себя как обычный клиент, только без экрана и устройств.
2. **Простая пересылка между участниками** без декодирования, для небольших комнат.
3. **Полноценный SFU**: сотни и тысячи соединений в процессе, пересылка RTP без декодирования, выбор слоёв simulcast/SVC под каждого получателя, оценка полосы и обработка NACK/PLI/TWCC за каждого, ICE-lite на одном порту.

API W3C и libwebrtc рассчитаны на конечную точку. Продакшн-SFU строят на отдельных лёгких стеках: Pion у LiveKit, свой C++ у mediasoup, Kotlin/Java у Jitsi Videobridge ([обзор](../research/existing-solutions.md)).

## Решение

| Класс | Где | Когда |
|---|---|---|
| 1. Серверный участник | `krtc-core` на таргетах `jvm`, `linuxX64`, `linuxArm64` в режиме без устройств: dummy ADM, пользовательские источники и приёмники ([ADR-0006](0006-media-io.md)), одна фабрика на много соединений ([ADR-0005](0005-threading.md)) | В скоупе 1.0 |
| 2. Пересылка закодированных кадров | `krtc-core`: Encoded Transform (`RTCRtpScriptTransform`, `generateKeyFrame`, `sendKeyFrameRequest`) + API вставки закодированных кадров в отправитель | В скоупе 1.0 (M5) |
| 3. SFU | Отдельный модуль `krtc-sfu` на `krtc-protocol` ([ADR-0007](0007-module-structure.md)), без libwebrtc | После 1.0, отдельный проект |

**Принципы для `krtc-sfu`:**
- **Sans-IO ядро** (как str0m): протоколы, маршрутизация и оценка полосы — чистые функции над пакетами и временем. Сокеты, потоки и таймеры живут снаружи, поэтому ядро тестируется детерминированно.
- **Транспорт:**
  - ICE-lite, DTLS-SRTP (DTLS — через проверенную библиотеку, а не свою криптографию), один UDP-порт на много клиентов;
  - TCP/TLS fallback;
  - на JVM — Netty или NIO, на Native — свой event loop.
- **Медиа:**
  - пересылка RTP с переписыванием SSRC, seq и timestamp;
  - выбор слоёв simulcast (RID) и SVC (Dependency Descriptor);
  - NACK/RTX, PLI/FIR, TWCC, REMB, оценка полосы на каждого получателя.
- **Ориентиры:** Jitsi Videobridge (Kotlin/Java) — архитектура маршрутизации; mediasoup — модель Producer/Consumer; LiveKit — сигнализация комнат.
- **Interop-проверка:** браузеры и krtc-клиенты как участники.

**Наблюдать за [W3C RTP Transport](https://w3c.github.io/webrtc-rtptransport/):** если спецификация стабилизируется и появится в libwebrtc, класс 2 станет пакетным, а граница между `krtc-core` и `krtc-sfu` сдвинется.

## Альтернативы

- **SFU на libwebrtc** (по PeerConnection на участника, пересылка через Encoded Transform): тяжело на одно соединение (потоки, буферы, декодер на приёме), нет управления слоями на уровне RTP. Годится для класса 2, не для 3.
- **Встроить Pion или mediasoup через FFI**: чужой рантайм (Go) или процесс-воркер (mediasoup). Возможно как временное решение для проекта, которому SFU нужен до готовности `krtc-sfu`, но не как часть krtc.

## Последствия

- Уже сейчас `krtc-protocol` проектируется так, чтобы его хватило серверу: полный разбор RTP/RTCP, а не только то, что нужно клиенту.
- Для класса 1 в план сборки libwebrtc добавляется конфигурация Linux без аудио- и видеоустройств и X11.
- `krtc-sfu` получит свой план и ADR, когда начнётся.

## Как проверить / когда пересмотреть

- Класс 1: пример бота записи на `jvm` (Linux) в samples, M2–M3.
- Класс 2: пример пересылки кадров между двумя соединениями на Encoded Transform, M5.
- Класс 3: пересмотреть после 1.0 с учётом статуса RTP Transport.
