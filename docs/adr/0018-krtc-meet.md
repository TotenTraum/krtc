# ADR-0018. `krtc-meet`: пример приложения для звонков на Compose Multiplatform

- Статус: Принято, этапы M4–M5 впереди
- Дата: 2026-11-11
- Уточняет: [ADR-0012](0012-kmp-client.md), [ADR-0014](0014-spike-krtc-native.md)

## Контекст

Библиотека умеет звонок, simulcast, показ экрана со звуком и сообщения комнаты (ADR-0015 – ADR-0017). Но приложения на ней нет. Неудобные места API (доступ к кадрам, выключение звука и видео, переподключение, выбор устройств) видны только из настоящего приложения. Оно нужно и как образец для тех, кто встраивает krtc.

## Решение

Модуль `krtc-meet`: один код интерфейса на Compose Multiplatform поверх `krtc-client` и `krtc-native`.

| Платформа | Как |
|---|---|
| macOS, Windows, Linux | Compose Desktop на JVM. `krtc-native` через JNI: dylib и `krtc.dll` в jar. Для Linux на JVM нужна своя JNI-библиотека, её пока нет |
| Android | Compose, `krtc-native` через JNI (M2) |
| iOS | Compose (`ComposeUIViewController`), `krtc-native` на Kotlin/Native (M2) |

Устройство:
- **`MeetSession`** (commonMain) — состояние звонка поверх `RoomClient`: вход, участники, речь, экраны, выключение микрофона и камеры. Отдаёт всё через `StateFlow`.
- **`VideoView(track)`** — кадры из `NativeTrack.setFrameListener` (ARGB) идут в переиспользуемые Skia-битмапы с двойной буферизацией. Новый кадр выводится на ближайшем кадре Compose, старые отбрасываются.
- **Платформенное** (`expect/actual`): фабрика и звук, камера, ARGB → `ImageBitmap`.

Этапы:
1. **M1, desktop на macOS:** вход, своё и чужое видео, звук. Режим тестового звука и тестовой картинки, чтобы проверять без микрофона и камеры.
2. **M2:** Android и iOS.
3. **M3:** выбор камеры и микрофона, показ экрана со звуком, чат, состояние «выключен» видно собеседникам (правки в SFU и сигнализации). Добавлены подписка на потоки, громкость собеседников, обработка микрофона.
4. **M4:** переподключение WebSocket, индикатор качества, раскладки, слой simulcast по размеру плитки.
5. **M5:** сборки dmg, msi, deb, APK и iOS в CI; JNI-библиотека для Linux на JVM.

## M1 (2026-11-11)

- Модуль `krtc-meet` (Compose Multiplatform 1.12.2, JVM): `MeetSession`, `VideoView` с тройной буферизацией, экраны входа и звонка. Звонок: сетка плиток с подсветкой говорящего, экраны собеседников отдельными плитками, кнопки микрофона, камеры и выхода.
- Упаковка: `createDistributable` и `packageDmg`, `.app` с описаниями доступа к камере и микрофону. Переменные окружения `KRTC_MEET_*` позволяют входить автоматически и снимать снимок окна для проверок.
- Проверено: приложение с тестовой картинкой и тестовым звуком в комнате с двумя вкладками Chrome. Chrome получает его видео и звук без потерь. Приложение выводит своё превью и видео Chrome (снимок интерфейса, отрисованный Compose вне экрана), подсвечивает говорящих.
- Не проверено: настоящие камера и микрофон (`PLATFORM`) в `.app` с описаниями доступа — запуск владельцем проекта.

## M2 (2026-11-11)

- `krtc-meet` получил таргеты Android (`com.android.kotlin.multiplatform.library`, `compileSdk` 37, как требует Compose 1.12) и iOS.
- Разница платформ спрятана за `MediaPlatform`:
  - `NativeMediaPlatform` — desktop и iOS, звук и камеры через libwebrtc;
  - `AndroidMediaPlatform` — синтетический звук плюс `AndroidAudio`, камеры через Camera2 (`AndroidCamera`).
- Вывод кадров:
  - Android — `android.graphics.Bitmap.setPixels`;
  - iOS — Skia, как на desktop.
- Отступы безопасной области (`WindowInsets.safeDrawing`) в общем `App`. Кнопки звонка переносятся на узком экране.
- Приложения:
  - модуль `krtc-meet-android`;
  - iOS-приложение для симулятора без проекта Xcode: Kotlin `main` с `UIApplicationMain` и `AppDelegate`, `Info.plist`, подпись ad-hoc (`assembleIosSimulatorApp`).
- CI: артефакты `krtc-meet-android` и `krtc-meet-ios`.
- Проверено в звонке с Chrome через `krtc-sfu-server`:

  | Платформа | Результат |
  |---|---|
  | Android 16 (эмулятор) | С тестовой картинкой: Chrome получает 1280×720 без потерь. С виртуальной камерой эмулятора и `AndroidAudio`: 720×1280. Приложение показывает видео Chrome |
  | iOS 26 (симулятор) | Тестовая картинка и звук: Chrome получает видео и звук без потерь. Приложение показывает видео Chrome |
- Не проверено: устройства (iPhone с подписью, телефон Android), камера iOS (в симуляторе её нет).

## M3 (2026-11-11)

- **Состояние «выключено» видно всем.**
  - Сигнализация: `ClientMessage.MediaState(audioMuted, videoMuted)` от клиента, `ServerMessage.PeerState` всей комнате, включая самого участника. Начальное состояние приходит в `PeerInfo` в `Welcome`.
  - Сервер объявляет выключенным, если выключил клиент или хост (`setMuted`).
  - API хоста: `ParticipantInfo.audioMutedByClient` и `videoMutedByClient`, событие `SfuEvent.MediaStateChanged`.
  - Клиент: `RoomClient.setMediaState` (можно до входа), `RemoteParticipant.audioMuted` и `videoMuted`.
- **Подписка на потоки.** `ClientMessage.Subscribe(peer, feed = camera | screen, enabled)`. SFU перестаёт пересылать этот поток подписчику (экран вместе со звуком) и не учитывает его в распределении полосы. При возобновлении поток идёт с ключевого кадра, нумерация непрерывна. m-line не пересогласуются. Клиент: `RoomClient.setSubscribed`, `RemoteParticipant.screenSubscribed`.
- **`krtc-native`:**
  - `NativeTrack.setVolume(0..10)` — громкость принятого звука (`AudioSource::SetVolume`);
  - `setAudioProcessing(echoCancellation, noiseSuppression, autoGainControl)`. Фабрика создаёт обработку звука (APM) сама и держит ссылку на неё. Автоусиление — это адаптивное цифровое усиление (AGC2) и аналоговое AGC1, которое на desktop меняет громкость входа ОС. Опции новых микрофонных треков берутся из тех же настроек.
- **Приложение:**
  - показ экрана с выбором источника и звуком;
  - на Android: системное окно согласия через `ActivityResult`, захват через `AndroidScreenCapture`;
  - чат (тема `chat`) с непрочитанными;
  - громкость на плитках;
  - «Подключиться» / «Отключиться» на чужом экране;
  - обработка микрофона в меню «Звук». При смене обработки во время звонка трек микрофона пересоздаётся, чтобы libwebrtc взял новые опции;
  - на тестовой странице сервера: кнопка микрофона и показ состояния «выключено».
- **Найдено и исправлено по пути:**
  - SFU собирал SDP предложения и `mids` из разных чтений состояния. Если ответ публикующего приходил между ними, m-line камеры была `sendonly`, но в `mids` её не было: клиент терял видео собеседника до конца звонка. Теперь оба строятся из одного снимка.
  - Синтетическое аудиоустройство (Android, тестовый звук) могло вызывать libwebrtc после возврата из `StopPlayout` и `StopRecording`. При выходе из звонка это падение в микшере. Теперь `Stop*` ждут текущий вызов.
  - Вызовы на закрытом `RTCPeerConnection`, transceiver или треке (выход во время согласования) обращались к освобождённой памяти. Теперь дескрипторы защищены блокировкой: после закрытия вызовы бросают исключение или ничего не делают. Transceiver, заменённый новым `OnTrack`, освобождается при закрытии, а не на потоке signaling libwebrtc: иначе возможна взаимная блокировка.
  - `RoomClient.join`, отменённый в момент рукопожатия WebSocket, оставлял на сервере участника-призрака до таймаута ICE. Теперь сокет закрывается.
  - `MeetSession` отменяет незавершённый вход при выходе из звонка.
- **Проверено:**

  | Что | Как | Результат |
  |---|---|---|
  | Все функции M3 | `MeetSessionTest`: два `MeetSession` с libwebrtc и встроенный SFU, 10 прогонов подряд | Состояние «выключено», чат в обе стороны, экран останавливается при отписке (кадры не растут) и возобновляется. Громкость 0 даёт тишину, 1 возвращает звук. После смены обработки звук идёт. Выход в любой момент согласования без падений и призраков |
  | Desktop | Против Chrome | Плитка «микрофон выключен», экран Chrome отдельной плиткой с «Отключиться», «Чат (1)» |
  | Android 16 (эмулятор) | Против Chrome | Сообщение из приложения пришло в Chrome. Показ всего экрана через системное окно: Chrome получает 864×1920 без потерь. Отключение и подключение к экрану Chrome. Выход во время показа без падения |
- Не проверено:
  - iOS (только сборка);
  - показ экрана на macOS (у процесса из этой сессии нет разрешения Screen Recording);
  - на слух: работа автоусиления и шумоподавления на настоящем микрофоне. Проверено только, что настройки применяются и звук не пропадает.
- В тесте обработка звука выключена: обе стороны шлют одинаковый тон 440 Гц, эхоподавление принимает свой тон за эхо чужого, а шумоподавление убирает ровный тон.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Отдельные нативные приложения (SwiftUI, Jetpack Compose, Swing) | Втрое больше кода, а цель — проверить общий KMP-API |
| Desktop без JVM (K/N + Skiko) | Compose UI под Linux и Windows на K/N нет, для macOS он экспериментальный. Нужен свой хост окна и ввода |
| Вывод видео через `SurfaceView` / `MTKView` / `Canvas` по платформам | Быстрее, но это три разных кода. Сначала общий путь через ARGB; если не хватит, вывод I420 в GPU-текстуру |

## Риски

- **Копирование ARGB.** Четыре плитки 720p30 — это около 400 МБ/с. Ограничиваем слоем simulcast по размеру плитки (M4); дальше — I420 в GPU.
- **Звук `PLATFORM` на desktop мало проверен:** эхоподавление, выбор устройств.
- **Windows и iOS на устройствах** проверяет владелец проекта.
