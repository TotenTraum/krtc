# ADR-0010. SFU `krtc-sfu` раньше 1.0: архитектура голосового сервера

- Статус: Принято (прототип работает, см. «Как проверено»)
- Дата: 2026-11-09
- Частично заменяет: [ADR-0009](0009-server-side-use.md) — сроки класса 3 (SFU). Принципы ADR-0009 остаются в силе.

## Контекст

ADR-0009 откладывал полноценный SFU до выхода 1.0. Приоритет изменился: нужен сервер голосовых комнат под высокую нагрузку (класс задач Discord), и он не зависит от сборки libwebrtc ([ADR-0001](0001-engine-libwebrtc.md)). Его можно строить сразу на `krtc-protocol` ([ADR-0007](0007-module-structure.md)).

## Решение

**Модули:**
- `krtc-protocol` — чистый Kotlin, все таргеты, без ввода-вывода: STUN (+ HMAC-SHA1 и CRC32 на чистом Kotlin), RTP-заголовки и расширения (RFC 8285), SDP (RFC 8866), демультиплексирование по RFC 7983.
- `krtc-sfu` — JVM 21: транспорт, DTLS, SRTP, комнаты, сигнализация.

**Транспорт:**
- **ICE-lite** (RFC 8445 §2.5) на одном UDP-порту для всех клиентов. Участник определяется по `USERNAME` в STUN, дальше — по адресу отправителя.
- **Сокеты.** На порту несколько сокетов с `SO_REUSEPORT`, по одному на шард: JDK сериализует `DatagramChannel.send` на блокировке канала. На Linux ядро ещё и распределяет входящие пакеты между сокетами.
- **DTLS 1.2** на BouncyCastle (`bctls`):
  - сервер всегда `setup:passive`;
  - сертификат клиента обязателен и сверяется с `a=fingerprint` из ответа;
  - рукопожатие идёт на виртуальном потоке — тысячи сессий не занимают системных потоков.
- **SRTP** — своя реализация поверх JCE (AES-NI):
  - профили `AEAD_AES_128_GCM` (предпочтительный) и `AES128_CM_HMAC_SHA1_80`;
  - KDF по RFC 3711, оценка ROC, окно защиты от повторов на 64 пакета;
  - проверено векторами RFC 3711 B.3 и RFC 7714 §16.1.1.

**Медиа-план** — SFU всегда отправляет offer (JSEP), поэтому сам выбирает payload type, id расширений и SSRC:
- **m-line 0** — микрофон участника (`recvonly` на стороне SFU).
- **m-line 1..n** — по одному на каждого другого участника (`sendonly`, SSRC назначает SFU). Слоты ушедших участников становятся `inactive` и переиспользуются следующими, поэтому SDP не растёт бесконечно.
- **Переписывание SSRC, seq и timestamp** на исходящем потоке сохраняет непрерывность, если клиент сменил трек.
- **Расширение `ssrc-audio-level`** (RFC 6464) — источник индикатора «говорит». SFU рассылает его по сигнализации.
- **Переговоры сериализованы:** пока offer не получил ответа, следующий ставится в очередь.

**Модель потоков:**
- **Шард** — однопоточный исполнитель. Комната целиком живёт в одном шарде (`hash(room) mod shards`), поэтому состояние медиа не требует блокировок, а комнаты масштабируются по ядрам.
- **Горячий путь пакета:** расшифровка один раз, затем для каждого слушателя — переписать заголовок, зашифровать его ключом, `sendto`.
- **RTCP** в первой версии завершается на SFU и не пересылается.

**Сигнализация:**
- WebSocket (Ktor CIO), JSON: `welcome`, `offer`, `answer`, `peer-joined`, `peer-left`, `speaking`.
- Очередь исходящих сообщений ограничена: медленный клиент отключается, а не раздувает память сервера.
- Проверка согласия (consent): участник отключается, если 30 секунд нет STUN-запросов.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| SFU на libwebrtc | Тяжело на одно соединение, нет управления пакетами (ADR-0009) |
| DTLS своими силами | Криптографический протокол с историей уязвимостей. BouncyCastle — проверенная реализация (её же использует Jitsi) |
| SRTP через BouncyCastle или libsrtp (JNI) | JCE с AES-NI быстрее BouncyCastle-AES, а JNI усложняет сборку. Своя реализация — около 200 строк, проверена векторами RFC |
| Клиент отправляет offer | Тогда SFU пришлось бы переназначать payload type и id расширений у каждого клиента и переписывать их при пересылке |
| Один сокет на всё | Измерено: многоядерная пересылка упирается в блокировку `DatagramChannel` (96 тыс. пакетов/с на 5 шардов против 192 тыс. с отдельными сокетами) |

## Последствия

- Сервер голосовых комнат работает с браузерами без libwebrtc и без нативного кода.
- Производительность на ядро определяется системным вызовом `sendto`, а не криптографией. Для Linux следующий шаг — `sendmmsg`/GSO через Panama FFM (JVM 22+).
- Видео, simulcast, RTCP-обратная связь и оценка полосы — следующий этап (см. «Дальше»).

## Как проверено

- **Модульные тесты:** векторы RFC 5769 (STUN), RFC 3711, RFC 7714 (SRTP), RFC 2202 (HMAC); переговоры (вход, выход, повторное использование слота, сериализация offer'ов).
- **Браузер (Chromium):**
  - 2–3 участника в одной комнате слышат друг друга, ~37 пакетов/с с тестовым сигналом (DTX в паузах), потерь 0, ненулевой `audioLevel`;
  - вход и выход посреди звонка, повторное использование слота;
  - индикатор «говорит».
  - На сервере: `srtpFailures=0`, `stunRejected=0`, `dtlsFailed=0`.
- **Бенчмарк** `./gradlew :krtc-sfu:benchmark` (MacBook, 10 ядер, JDK 24, loopback):

| Измерение | Результат |
|---|---|
| Только криптография (расшифровка + перешифровка), 1 ядро | ~1,7 млн исходящих пакетов/с (GCM) |
| С `sendto`, 1 ядро | ~120 тыс. пакетов/с ≈ 2 400 потоков-слушателей Opus по 50 пакетов/с |
| 5 шардов с `sendto` | ~190 тыс. пакетов/с ≈ 3 800 слушателей. На loopback macOS приёмник делит те же ядра, на Linux и реальной сети ожидается лучше — нужно перемерить |

## Дальше

1. Видео: VP8/H.264, simulcast (RID) с выбором слоя под получателя, PLI/FIR, NACK/RTX.
2. RTCP: пересылка SR для синхронизации, SRTCP, TWCC и оценка полосы на получателя.
3. Ввод-вывод: пул буферов вместо выделения памяти на каждый пакет, `sendmmsg`/GSO на Linux.
4. Масштабирование на несколько узлов: маршрутизация комнат по узлам, каскад SFU для больших комнат.
5. Пересылка только активных говорящих (last-N) для больших комнат.
6. Авторизация в сигнализации (токены), TURN/TCP для клиентов за строгим NAT, IPv6.
