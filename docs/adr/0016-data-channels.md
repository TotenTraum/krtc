# ADR-0016. Data channels: SCTP в `krtc-sfu`, `RTCDataChannel` в клиенте

- Статус: Принято
- Дата: 2026-11-10
- Уточняет: [ADR-0010](0010-sfu-before-1.0.md), [ADR-0012](0012-kmp-client.md), [ADR-0013](0013-embeddable-sfu.md)

## Контекст

До этого решения data channels не было ни в SFU, ни в клиенте. Приложениям для звонков нужны чат, реакции, состояние комнаты (поднятая рука, курсоры, общий документ). Без data channels это приходится гнать через сигнализацию хоста, а она не рассчитана на поток и не умеет отдавать «последнее значение без повторов».

Какие ограничения учитывались:
- SFU — DTLS-сервер (`a=setup:passive`) и всегда отправитель предложения. Браузер — DTLS-клиент, он сам начинает SCTP.
- В Kotlin Multiplatform нет готового SCTP: usrsctp и dcsctp — C/C++, их сборка под JVM и K/N по всем платформам — отдельный проект (ADR-0011).
- Хост встраивает SFU (ADR-0013) и должен решать, что пропускать: модерация, сообщения на сервер, ограничение получателей.

## Решение

### 1. SCTP поверх DTLS в `krtc-sfu` на Kotlin (`krtc.sfu.sctp`, общий код)

`SctpAssociation` — ассоциация RFC 9260 в объёме, нужном WebRTC (RFC 8831):
- **рукопожатие:** INIT, INIT ACK, COOKIE ECHO, COOKIE ACK. SFU отвечает; роль инициатора есть для тестов;
- **данные:** DATA с фрагментацией и сборкой, упорядоченная и неупорядоченная доставка, SACK с gap-блоками и дубликатами;
- **надёжность и перегрузка:** таймер T3, быстрая повторная передача после трёх отчётов о пропуске, cwnd/ssthresh (slow start, congestion avoidance, fast recovery), RTO по RFC 6298;
- **частичная надёжность (RFC 3758):** лимит повторов и время жизни сообщения; брошенные сообщения пропускаются через FORWARD-TSN с SSN для упорядоченных потоков;
- **сброс потоков (RFC 6525):** закрытие каналов; входящие запросы откладываются, пока не придут все данные до Sender's Last TSN;
- HEARTBEAT ACK, ABORT, SHUTDOWN.

Не сделано:
- I-DATA (RFC 8260) — SFU его не объявляет;
- планировщики потоков;
- собственный HEARTBEAT — живость соединения проверяет ICE consent;
- перезапуск с сохранением состояния — новый INIT открывает новую ассоциацию.

Пакет SCTP ограничен 1200 байт, чтобы DTLS-запись проходила по пути IPv6 с MTU 1280, в том числе через ICE-TCP.

`DataChannels` поверх ассоциации:
- DCEP (RFC 8832): DATA_CHANNEL_OPEN и ACK; до ACK сообщения идут упорядоченно;
- кадры по PPID: строка, двоичные данные, пустые сообщения;
- чётность идентификаторов потоков: у DTLS-сервера нечётные;
- закрытие с ответным сбросом своей стороны.

`DtlsEndpoint` теперь передаёт прикладные данные в обе стороны:
- JVM: `DTLSTransport` BouncyCastle, запись под отдельной блокировкой;
- K/N: корутина, которой принадлежит `SSL`, выбирает через `select` между входящими записями и исходящими данными.

Все SCTP-операции участника выполняются в потоке шарда его комнаты, без блокировок, как и медиа. Таймеры срабатывают каждые 50 мс.

### 2. Модель комнаты: два канала и конверт (`krtc-signaling` `DataEnvelope`)

- SFU предлагает `m=application … UDP/DTLS/SCTP webrtc-datachannel` третьей m-line (mid `d`, `a=sctp-port:5000`, `a=max-message-size:65536`) в той же BUNDLE-группе.
- Клиент открывает (DCEP) два канала:
  - `krtc` — надёжный и упорядоченный;
  - `krtc-lossy` — неупорядоченный, `maxRetransmits: 0`.

  Каналы с другими метками SFU закрывает.
- Сообщение — двоичный конверт: `версия | число id | (длина, id)* | длина, тема | payload`.
  - От клиента к SFU: id — получатели; пусто значит все, кроме отправителя.
  - От SFU к клиенту: единственный id — отправитель; пусто значит сам сервер.
- SFU не смотрит в payload. Для каждого сообщения он:
  - вызывает `SfuConfig.dataPolicy` хоста: пропустить, изменить (тема, получатели, надёжность) или поглотить (`null`);
  - кодирует конверт с id отправителя один раз и рассылает получателям по каналу того же вида. Если у получателя нет канала `krtc-lossy`, сообщение идёт по надёжному.
- Хост пишет сам через `Sfu.sendData(room, payload, topic, to, reliable)`, политика к этому не применяется.
- **Защита памяти:**
  - если у получателя в очереди SCTP больше 4 МБ (надёжный канал) или 256 КБ (без повторов), сообщение ему не отправляется;
  - сообщения больше 64 КБ не принимаются.

  Счётчики в `SfuMetrics`: `dataMessagesIn`, `dataMessagesOut`, `dataMessagesDropped`.

### 3. Клиент

- **`krtc-core`:** `RTCDataChannel` (W3C) с `readyState: StateFlow`, `onmessage: Flow<RTCDataChannelMessage>` (`Text` или `Binary`), `send(String | ByteArray)`, `bufferedAmount`, `close()`. В `RTCPeerConnection` — `createDataChannel(label, RTCDataChannelInit)` и `ondatachannel: Flow`.
- **`krtc-native`:**
  - C API `krtc_data_channel_*` поверх `DataChannelInterface` из libwebrtc;
  - Kotlin/Native через cinterop, JVM и Android через JNI.
  - Сообщения копятся в канале на 4096 штук, пока их не заберут, в том числе пришедшие до подписки. Каждое сообщение получает один подписчик.
- **`RoomClient`:**
  - создаёт оба канала, когда предложение несёт SCTP m-line;
  - `sendData(payload, topic, to, reliable)` — `false`, пока канал не открыт;
  - `data: SharedFlow<RoomData>` (`from`, `topic`, `payload`, `reliable`), `dataOpen: StateFlow<Boolean>`.
- **Тестовая страница `krtc-sfu-server`:** чат поверх того же конверта; `krtc.sendData(...)` и `krtc.messages` для автоматических проверок.

## Проверка (2026-11-10)

| Что | Как | Результат |
|---|---|---|
| SCTP в модели | `SctpTest`: две ассоциации через канал с задержкой, перестановкой и потерями | Рукопожатие и DCEP в обе стороны; 200 сообщений (до 5 КБ, с фрагментацией) при 10 % потерь — все и по порядку; без повторов при 20 % потерь — потеряна часть, поток не встаёт, очередь пуста; `maxRetransmits: 1` при 30 % — по порядку, без остановок; закрытие сбрасывает потоки с обеих сторон, данные до закрытия доходят |
| Ретрансляция в комнате | `DataRelayTest`: три участника, SFU, клиентские SCTP-концы без DTLS | Адресация (`to`), надёжный канал и канал без повторов, политика поглощает тему, `sendData` хоста, 60 КБ одним сообщением |
| Chrome ↔ SFU (K/N) | Две вкладки | SCTP `connected`, `maxMessageSize` 65536; 3000 надёжных сообщений по 1 КБ — все по порядку; 60 КБ одним сообщением; 200 без повторов; канал `other` открылся и закрылся сбросом потока |
| Chrome ↔ SFU (JVM, BouncyCastle) | Две вкладки | 2000 надёжных по порядку, 60 КБ одним сообщением |
| Нативный клиент | `krtc-native-demo … chat` (macOS K/N и JVM) вместе с Chrome | Сообщения в обе стороны; `tick` без повторов приходит с `reliable=false` |
| Клиент | `RoomClientSfuTest` с фейковым `RTCPeerConnection` | Каналы создаются из предложения, ответ принимает SCTP m-line, конверт кодируется и разбирается |

## Альтернативы

| Вариант | Почему нет |
|---|---|
| usrsctp или dcsctp через cinterop/JNI | Ещё одна нативная зависимость SFU под каждую платформу и JVM, ломает «чистый» JVM-артефакт. Нужная часть RFC — около 1200 строк общего Kotlin |
| Сообщения через сигнализацию (WebSocket хоста) | Нет режима без повторов; head-of-line blocking на TCP; нагрузка на канал управления. Остаётся для управляющих сообщений |
| Прозрачная ретрансляция любых каналов «как есть» | Получатель не знает отправителя, хост не может фильтровать, нужно зеркалить DCEP на каждого участника. Конверт проще и даёт адресацию |
| Каналы по одному на пару участников | Число потоков SCTP растёт квадратично, сложная синхронизация открытия. Два канала на участника хватает |

## Последствия

- В предложении SFU появилась m-line `d`: при включённых data channels медиа-слоты начинаются с четвёртой m-line. Клиенты, сопоставляющие m-line по `mids`, этого не замечают. `SfuConfig.dataChannels = false` возвращает прежнюю раскладку.
- Изменения API:
  - `RTCPeerConnection` получил `createDataChannel` и `ondatachannel` — сторонние реализации `krtc-core` должны их добавить;
  - `SfuMetrics` получил три поля.

  ABI обновлён.
- Метки `krtc` и `krtc-lossy` и формат конверта — часть протокола SFU. Его версия — первый байт конверта.
- Нерешённое:
  - I-DATA (чередование больших сообщений на одном потоке);
  - приоритеты каналов;
  - отдельный лимит частоты сообщений на участника. Сейчас защищают только размеры очередей и политика хоста.
