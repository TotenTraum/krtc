# ADR-0015. Транспорт и управление перегрузкой в `krtc-sfu`

- Статус: Принято
- Дата: 2026-11-10
- Уточняет: [ADR-0010](0010-sfu-before-1.0.md), [ADR-0013](0013-embeddable-sfu.md)

## Контекст

`krtc-sfu` встраивается в сервер пользователя (ADR-0013) и должен работать в реальных сетях. Перед этим решением:
- **Оценки канала не было.** Отправителям SFU раз в секунду слал REMB с фиксированными 2,5 Мбит/с. Слой simulcast для получателя выбирался только по его желанию (q/h/f), а не по его каналу. Слабый канал получателя забивался верхним слоем, видео замирало.
- **Сокеты.** SFU слушал один адрес. С `0.0.0.0` ответы уходили не с того адреса, куда писал клиент, и libwebrtc их отбрасывал (ADR-0014, «Звонок»), поэтому `--bind` был обязателен. IPv6 не поддерживался.
- **Только UDP.** В сетях с закрытым UDP (корпоративные прокси, часть гостевых Wi-Fi) соединиться было нельзя.
- **Смена сети.** При смене сети клиента (Wi-Fi ↔ LTE) соединение не восстанавливалось.

## Решение

### 1. transport-cc (draft-holmer-rmcat-transport-wide-cc-extensions-01)

Расширение transport-wide sequence number (id 5) и `a=rtcp-fb:* transport-cc` предлагаются на всех m-line в обе стороны. `krtc-protocol`: `TransportCc` — запись и чтение номера, сборка feedback (векторы двухбитных статусов), разбор feedback (все три вида чанков).

**От отправителя к SFU.** `TwccReceiver` запоминает время прихода каждого номера (UDP-поток засекает время до очереди шарда). Каждые 50 мс SFU шлёт отправителю feedback. Его собственный GCC (Chrome, libwebrtc) сам подбирает битрейт. REMB остаётся потолком.

**От SFU к получателю.** SFU ставит в каждый пересылаемый пакет свой номер для этого получателя, включая RTX. `SendSideBwe` по feedback получателя оценивает канал — компактный GCC (draft-ietf-rmcat-gcc):
- **по задержке:** группы пакетов по 5 мс → вариация межгрупповой задержки → наклон trendline по 20 точкам → перегрузка или недогрузка относительно адаптивного порога → AIMD: при перегрузке 0,85 × подтверждённого битрейта, иначе рост 8 %/с;
- **по потерям:** больше 10 % — снижение на половину доли потерь, меньше 2 % — можно расти;
- **без probing:** оценка не уходит дальше 1,5 × подтверждённого + 1 Мбит/с.

**Распределение слоёв.** Раз в 100 мс для каждого получателя:
- бюджет = оценка − 64 кбит/с на каждый аудиопоток;
- пока не влезает, самый дорогой поток опускается на слой ниже;
- затем потоки поднимаются, пока всё влезает в 85 % бюджета (гистерезис).

Битрейт слоя измеряется на входе. Переключение происходит на ключевом кадре (как и раньше). Получатель без transport-cc не ограничивается.

Наблюдаемость: `Sfu.linkStats()` (оценка, подтверждённый битрейт, потери, слой от каждого отправителя), `GET /stats` в `krtc-sfu-server`.

### 2. Сокет на каждый локальный адрес вместо `IP_PKTINFO`

Wildcard-bind разворачивается в адреса интерфейсов:
- `0.0.0.0` — все IPv4;
- `::` — все IPv4 и IPv6, link-local IPv6 пропускается.

На каждый адрес открывается своя группа сокетов (по одному на шард, SO_REUSEPORT). `PeerAddress.via` запоминает группу, ответ уходит через неё, то есть с того адреса, на который писал клиент.

| | Сокет на адрес | `IP_PKTINFO`/`IPV6_PKTINFO` |
|---|---|---|
| JVM | Работает (NIO) | В NIO недоступно |
| Kotlin/Native | Работает (POSIX) | Нужны `recvmsg`/`sendmsg` с cmsg, разные на Linux и macOS |
| Новые адреса в процессе работы | Не подхватываются (нужен перезапуск) | Подхватываются |

Выбрано одинаковое поведение на обеих платформах. Динамические адреса (DHCP, VPN) — известное ограничение.

`SfuConfig.announcedAddresses` (`--announce a,b`): несколько host-кандидатов по убыванию предпочтения, IPv4 и IPv6.

### 3. ICE-TCP (RFC 6544, кадры RFC 4571)

- `TcpServer` слушает тот же порт на тех же адресах. Кандидаты `tcptype passive`, type preference 80 (ниже UDP), так что TCP выбирается, только если UDP не прошёл.
- Соединение — это `PeerAddress` с `tcp = true`. `Transports` направляет отправку в UDP или TCP. STUN, DTLS и SRTP идут тем же путём.
- Не больше 4096 соединений. На JVM — виртуальный поток на соединение, на Kotlin/Native — поток на соединение.
- Опции `iceTcp` (по умолчанию включено) и `iceUdp` (`false` — только TCP; для сетей без UDP и для тестов).

### 4. ICE restart (RFC 8445 §9)

- `ClientMessage.RestartIce`: SFU выдаёт новые ufrag/pwd и шлёт новое предложение.
- Проверки со старой парой принимаются, пока клиент не перейдёт на новую. DTLS и SRTP не перезапускаются.
- `RoomClient` просит перезапуск сам: сразу при `FAILED` или через 2 с в `DISCONNECTED`, затем повторяет каждые 5 с. Публичный `restartIce()` — для приложений, которые узнают о смене сети раньше.

## Проверка (2026-11-10)

| Что | Как | Результат |
|---|---|---|
| transport-cc к отправителю | Chrome-издатель | `availableOutgoingBitrate` 2500 кбит/с (GCC Chrome работает по нашему feedback, потолок — REMB) |
| Оценка канала и слои | Два Chrome, `--simulate-downlink-kbps 200` | Старт на 1280 → 69 % потерь → оценка 100 кбит/с, слой q (320) → потери 0 → рост до ~170 кбит/с, слой h (640), ~160 кбит/с без потерь |
| То же без ограничения, лимит 600 кбит/с | — | Верхний слой тестовой анимации (~290 кбит/с) влезает и остаётся |
| Модель | `BweTest`: FIFO-канал 800 кбит/с | Оценка — пила 700–840 кбит/с; свободный канал — рост 8 %/с; 25 % потерь — спад до минимума |
| Wildcard-bind | `--bind ::`, нативный клиент (libwebrtc) | Соединяется без `--bind <IP>` (раньше `FAILED`) |
| IPv6 | Chrome, кандидат `::1` | Соединение по `udp ::1` |
| ICE-TCP | `--ice-udp false`, Chrome и нативный клиент | `tcp 127.0.0.1 passive`, DTLS, медиа в обе стороны, 0 ошибок SRTP |
| ICE restart | Нативный клиент, `restart-ice` | Новое предложение, видео без разрыва, 0 отклонённых STUN; `RoomClientSfuTest`: `FAILED` → новый ufrag |

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Только REMB, расчёт на приёмной стороне | Chrome почти не шлёт REMB при transport-cc; приёмная оценка хуже и не видит потери на пути от SFU |
| Отдать выбор слоя клиенту (он видит свой канал) | Клиент не знает, сколько стоит каждый слой; решения нескольких зрителей не координируются; ручной выбор q/h/f остаётся как потолок |
| Probing (padding RTX) для быстрого подъёма | Сложнее и тратит канал. Без него подъём слоя занимает секунды — приемлемо. Вернуться, если медленный подъём станет заметен |
| TURN вместо ICE-TCP | Отдельный сервер и лишний hop. ICE-TCP прямо в SFU закрывает основной случай (UDP запрещён, TCP разрешён) |

## Последствия

- `SfuConfig`: `announcedAddresses`, `iceTcp`, `iceUdp`, `simulatedDownlinkBps` (тесты). `Sfu.linkStats()`, `SfuLinkStats`. ABI обновлён.
- Порт сервера теперь занимается и под TCP.
- Wildcard-bind открывает `адреса × шарды` сокетов, например 4 × 10 = 40 на ноутбуке.
- Нерешённое:
  - probing;
  - TURN/TLS (TCP 443 через прокси);
  - подхват новых локальных адресов без перезапуска;
  - temporal layers (SVC) как ступени между слоями simulcast.
