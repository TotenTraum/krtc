# ADR-0003. JS и Wasm — прямой маппинг на браузерный API

- Статус: Предложено
- Дата: 2026-11-09

## Контекст

В браузере WebRTC уже есть, и он и есть эталон спецификации. Тащить туда libwebrtc (Wasm-сборка) бессмысленно: нет доступа к камере, сокетам UDP и аппаратным кодекам, а размер огромный.

## Решение

- Таргеты `js(browser)` и `wasmJs(browser)` реализуют общий API krtc поверх нативных объектов браузера через `external`-декларации.
- External-декларации генерируются из того же WebIDL (`@webref/idl`), что и `krtc-idl`, генератором в `tools/spec-inventory`. Так они не расходятся со спецификацией.
- Реализация — тонкие обёртки: Promise превращается в `suspend` через `await()`, события — в `Flow` через `addEventListener`.
- Возможности, которые есть только в браузере (например, `HTMLMediaElement.setSinkId`), пробрасываются как есть. Нативные аналоги проектируются в общем API ([ADR-0004](0004-api-model.md)).
- Node.js не поддерживается: там нет WebRTC без нативных аддонов.

## Альтернативы

- **libwebrtc в Wasm**: нет UDP, нет устройств, огромный размер. Отвергнуто.
- **Ручные external-декларации**: быстро устаревают и расходятся со спецификацией. Отвергнуто в пользу генерации.

## Последствия

- Покрытие на браузерных таргетах определяется браузером пользователя. Матрица покрытия для `js` и `wasmJs` честно отражает поддержку движков (Chromium, Firefox, Safari).
- Conformance-тесты WPT на этих таргетах можно гонять почти без адаптации.
- Различия Wasm и JS в interop (`JsAny` против `dynamic`) требуют двух слоёв деклараций или общего генератора с двумя выходами.

## Как проверить / когда пересмотреть

- Loopback в Chromium через Playwright на обоих таргетах в CI (этап 6).
